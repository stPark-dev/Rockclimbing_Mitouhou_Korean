# 초기 조사 — 락클라이밍 미답봉에의 도전 알프스 편 (PS1)

조사일 2026-10-21. 현재 확인된 구조만 적는다. 근거 산출물(RAM 덤프, VRAM 덤프, 화면)은 저장소 밖 `work/`에 있고, 재현 방법을 각 항목에 적는다.

## 1. 지원 원본

| 항목 | 값 |
|---|---|
| 제목 | ロッククライミング 未踏峰への挑戦 アルプス編 (일본판, SLPS-00662, ⓒ 위넷) |
| 구성 | bin/cue 22트랙. 트랙 1 `MODE2/2352` 데이터, 트랙 2–22 CD-DA |
| 트랙 1 크기 | 150,744,384 바이트 (64,092 섹터) |
| 트랙 1 SHA-256 | `86918cf6ae389bd0ef5ab264a0f172d8fcb9d70026a2f25cb7ec3fa9d4b9c6d8` |

- ISO 9660. PVD 볼륨 크기는 250,142 섹터로 오디오 트랙까지 덮는다. `CDDA/*.DA` 21개는 오디오 트랙을 가리키는 디렉터리 항목이다.
- 디렉터리 항목 618개 = CD-DA 21 + 영상 STR 58(`MOVIE/`, `MOVIE2/`; 그중 51개가 Form 2 섹터 포함) + 데이터 파일 539. 데이터 파일은 모두 Form 1이고 서브헤더는 본문 `00 00 08 00`, 마지막 섹터 `00 00 89 00`뿐이다.
- 트랙 1의 마지막 파일 `KABE.BIN`은 LBA 63,942에서 끝나고 트랙은 64,092 섹터다. 뒤쪽 여유는 약 150섹터(포스트갭일 수 있음, 미확인)라 **파일을 키워 뒤에 붙이는 방식은 기본으로 쓰지 않는다.** 바꾸는 파일은 원래 섹터 수 안에 들어가야 한다.
- 수정 대상은 트랙 1만이다. 오디오 트랙은 그대로 둔다.

## 3. 글꼴과 인코딩 (확인)

### 3.1 글꼴

- 12×12 픽셀, 4bpp 저장(실제 값 0–3, 2비트 안티에일리어싱), 글자당 72바이트, **1,348자**(97,056바이트).
- 같은 글꼴이 101개 파일에 바이트 단위로 똑같이 들어 있다: `MENU/KWAMENU.BIN` 오프셋 0, `X/X2.BIN`·`SUZU/XI*/SU_IG_*.BIN`·`SUZU/XM_SUZU/SU_MG_*.BIN` 오프셋 0x3E4, `X/X0.BIN` 0x6AC0C, `X_HUMAN/X_STAFF.BIN` 0x1DD90. 각 파일이 실제로 어느 화면의 글꼴 공급원인지는 메뉴 화면(`MENU/KWAMENU.BIN`)만 확인했다.
- `MENU/KWAMENU.BIN` 전체(402,376바이트)가 RAM 0x800E8000에 그대로 올라온다(데이터베이스 화면 RAM 덤프와 전 구간 일치).
- 렌더러는 화면에 나오는 글자만 한 자씩 VRAM에 올린다(3×12 halfword = 12×12 4bpp 업로드, DuckStation VRAM 쓰기 덤프에서 94회 관찰). 업로드된 글리프는 RAM 글꼴 표의 해당 칸과 일치한다.
- 칸 배치: 0–9 숫자, 10–33 기호, 34–59 A–Z, 60–85 a–z, 86–162 히라가나, 163–239 가타카나, 240–251 기타(童 夢 ？ ー ’ ・ ゃゅょャュョ), 252부터 한자. 1262–1265는 △□○×. 전체 문자표는 `tables/charmap.tsv`(§3.4).
- 한자 칸에는 같은 한자 블록이 여러 번 반복된다(비트맵이 완전히 같은 묶음 103개). 같은 글자의 안티에일리어싱만 다른 변형 칸도 있다.

### 3.2 문자 코드 (렌더러 코드로 확인)

메인 실행 파일의 렌더러(글리프 준비 단계 0x800173BC, 그리기 단계 0x80017770 부근)가 정의한다. 제어 코드는 두 단계 모두 `F8`–`FE` 분기표(0x800106EC, 0x8001070C)로 처리한다.

| 바이트 | 길이 | 의미 |
|---|---|---|
| `01`–`EF`, `F5`–`F7` | 1 | 글리프 `b − 1` (0–238, 244–246) |
| `F0`–`F4` `xx` | 2 | 글리프 `0xEF + ((b − 0xF0) << 8 \| xx)` (239–1347) |
| `F8 xx` | 2 | 표 0x800AA9B4[xx] 참조 (아이콘으로 추정) |
| `F9 xx` | 2 | 문자열 표 0x80070E10[xx]로 읽기 위치를 옮김 (끼워 넣는 문자열) |
| `FA xx` | 2 | 표 0x80081F94[xx]의 값을 10진수로 출력 |
| `FB xx yy` | 3 | 그리기 속성 설정 (색으로 추정, 미확인) |
| `FC xx` | 2 | x += xx × 13 (가로 띄우기) |
| `FD` | 1 | 전각 공백, x += 13 (예: 데이터베이스 설명 첫 줄 들여쓰기) |
| `FE` | 1 | 줄바꿈 |
| `FF` | 1 | 문자열 끝 |

근거: 화면 문장 「△（Ｒ１）ボタン（右手）」이 `KWAMENU.BIN` 0x17928에 `F3 FF 1B 34 02 1C EB B3 D1 1B F2 07 F0 3D 1C`로 있다(△=1262, （=26, Ｒ=51, １=1, ）=27, ボ=234, タ=178, ン=208, 右=758, 手=300). 같은 바이트가 RAM 0x800C7840에 있다. 처음에 `FD`를 쪽 시작으로 추정했으나, 그리기 단계 코드에서 13px 전진으로 확인해 바로잡았다. 문자열마다 포인터가 따로 있고, 여러 쪽짜리 설명은 쪽마다 별도 문자열이다.

- `FF`는 2바이트 코드의 둘째 바이트로도 나온다(`F3 FF`=△). 쪽 끝은 토큰 단위로 읽어야만 찾을 수 있다(`tools/textcodec.py` `read_page`). §4의 양 추정은 이 점을 반영하지 않은 바이트 스캔이라 경계가 일부 틀릴 수 있다.
- 렌더러(메인 실행 파일, 0x80017600 부근과 0x80017CC4 부근)는 `F0`–`F4`만 2바이트 선두로 받는다(`slti 0xF5`, `slti 0xF0`). `F5`–`FC`는 2바이트 코드가 아니다.

### 3.4 문자표 (2026-10-21)

`tables/charmap.tsv`, 1,348칸 전부. 상태 열:

| 상태 | 칸 수 | 뜻 |
|---|---|---|
| `visual` | 1,313 | 비트맵 육안 판독 |
| `context` | 30 | 원문 문맥으로 확정·교정 (예: 料→斜 「急斜面」, 開/閉 「開閉」, 遅→遥 「遥かなる」) |
| `unverified` | 5 | 루트 모듈 텍스트에 나오지 않음(664 稜, 691 愿, 708 迂, 742 崗, 1239 麗) |

방법과 근거:
- 0–251은 글꼴 배치 순서대로, 252–1347은 100자씩 확대 그림을 OCR 후보를 보지 않고 판독했다.
- 비트맵이 같은 103묶음에서 판독이 모두 일치했다.
- 판독과 OCR(Noto Sans CJK 템플릿 정합) 1위가 다른 226칸은 실제 문장 속 단어로 확인해 16칸을 교정했다. 루트 모듈 텍스트에서 3회 이하로 쓰인 한자가 든 줄 약 300개를 읽어 4칸을 더 교정했다.
- 남은 위험: OCR과 판독이 우연히 같게 틀린 칸, 문맥 확인을 거치지 않은 다회 사용 한자. 번역 작업에서 원문을 읽으며 이상한 단어가 나오면 이 표를 먼저 의심한다.
- 원문 자체의 오자로 보이는 것(「雪洞を掘って非難」, 「打ちんで」)은 글리프 문제가 아니라 그대로 둔다.
- 루트 텍스트에 쓰인 서로 다른 한자는 748종(바이트 스캔 기준 추정).

### 3.3 글자별 진행폭 (확인)

- 1,348바이트 폭 표가 `SLPS_006.62` 오프셋 0x35E80(RAM 0x80045680, t_addr 0x80010000 + 헤더 0x800)에 있다. 숫자 10, 소문자 3–11, 히라가나 9–12, 한자 대부분 13.
- 전역 플래그(gp+0x364)가 켜지면 고정폭 13을 쓴다. 어느 화면에서 켜지는지는 미조사.
- **원작 버그**: 비트맵 경로(0x80017604)는 2바이트 코드를 `((b−0xEF)<<8) − 0x11 + lo` = k로, 진행폭 경로(0x80017CCC)는 `− 0x10` = k+1로 해독한다. 그래서 2바이트 글자 k는 `폭표[k+1]`만큼 진행한다. 1바이트는 `폭표[k]`. 마지막 칸 1347은 표 밖 바이트를 읽으므로 한글 칸으로 쓰지 않는다.
- PoC에서 확인: 이 규칙대로 폭을 넣으면 겹침이 사라지고, 첫 시도처럼 칸 번호대로 넣으면 2바이트 글자 뒤가 겹친다.

## 4. 텍스트 위치와 양

### 4.1 모듈 적재 (실행 파일·오버레이 코드로 확인)

적재 함수는 `0x80012AE0(파일명, 주소)`. 오버레이 주소는 변수 `*(0x80010000)` = 0x800AFF18.

| 파일 | RAM 주소 | 불러오는 쪽 | 내용 |
|---|---|---|---|
| `KWAMENU`, `KABE`, `MESI`, `MGAME`, `STAFF`, `SUZU_0`, `SUZU_1` | 0x800AFF18 | 실행 파일 상태 분기(0x80013730 부근). `SUZU_0/1`은 `START.BIN`(0x801FFF04)의 함수 경유 | 코드 + 문자열 |
| `SUZU0`–`SUZU4` | 0x800CF984 | `SUZU_0`이 상태 값으로 하나 선택 | 문자열 + 절대 주소 포인터 구조체(파일 뒤쪽) |
| `MT0`, `MT1` | 0x800CF984 | `SUZU_1`이 선택 | 이벤트 메시지(악천후·낙석 등) |
| `X_SUZU` | 0x800DF3F0 | `SUZU_0`, `SUZU_1` | 짧은 문자열과 표 |
| `X/X2`, `X_HUMAN/*`, `SUZU/*` | 0x800F8000 | 각 오버레이 | 그래픽 묶음(글꼴 사본 포함) |

`SU_TOOL.BIN`은 실행 파일에 이름만 있고 디스크에 없다.

### 4.2 참조

- 메뉴 모듈은 문자열 후보의 대부분이 32비트 포인터 또는 `lui/addiu` 쌍으로 직접 참조된다.
- `SUZU1`–`4`는 파일 안에 0x800CF984 기준 절대 포인터 구조체가 있고, 대부분 문자열이 아니라 중간 구조체를 가리킨다. `SUZU0`, `MT0/1`은 직접 포인터가 거의 없다. 이들 문자열의 참조 경로는 미해결.
- 결론: 문자열 시작 위치를 옮기지 않는 **제자리 교체**를 기본으로 한다. 이 방식은 참조를 모두 몰라도 안전하다. 포인터가 확인된 문자열만 재배치 후보로 둔다.

### 4.3 채택한 문자열 모집단 (2026-10-21, `tools/textmap.py`)

판정 규칙(디코딩 모양만으로 채택하지 않음):
- 코드 모듈: 모듈 또는 실행 파일의 32비트 값·`lui/addiu` 쌍이 시작을 가리키는 문자열(`ref`), 그리고 그와 0–3바이트 `00`으로만 이어진 사슬의 문자열(`chain`). MIPS 바이트가 글자처럼 읽힌 것(글자 1개, 영문 소문자, `れ`+숫자·기호)은 제외.
- 텍스트 묶음(`SUZU0`–`4`, `MT0/1`): 파일 시작부터 이어지는 사슬 전체(`blob`). `MT0/1`은 0x17E8부터 숫자표라 제외.
- 제외 목록은 직접 검토했다. 실제 문장이 섞이지 않았음을 확인했고(개발용 「ｘｘ」 자리표시 문구는 채택), 개수는 `EXPECTED_COUNTS`로 고정했다. 빌드는 개수가 달라지면 멈춘다.

| 모듈 | 문자열 | 모듈 | 문자열 |
|---|---|---|---|
| KWAMENU | 731 | SUZU0 | 404 |
| KABE | 62 | SUZU1 | 550 |
| MESI | 22 | SUZU2 | 469 |
| STAFF | 1 | SUZU3 | 538 |
| SUZU_0 | 745 | SUZU4 | 472 |
| SUZU_1 | 268 | MT0 | 90 |
| X_SUZU | 115 | MT1 | 90 |

- 합계 4,557개 (blob 2,613, 나머지는 ref·chain). 원문이 서로 다른 것은 1,477개, 약 67,400자·108,000바이트(글자당 약 1.61바이트), 글리프 약 1,040종(한자 약 770).
- 수정 이력: 첫 채택(4,559개)은 코드 바이트 판정에 「れ」 대신 「る」(126)를 써서, 코드 바이트 14개를 남기고 「る、」가 든 진짜 문장 12개를 빠뜨렸다. 「れ」(127)로 고치고 쉼표·마침표를 판정에서 뺀 뒤 다시 검토해 4,557개로 고정했다.
- 같은 문장이 여러 모듈에 사본으로 있다(예: `SUZU_0`과 `SUZU0`–`4`, `X_SUZU`와 `KWAMENU`의 스테이지 이름). 번역은 원문 단위로 하고 모든 사본에 적용한다.
- `MGAME`(미니게임)은 채택된 문자열이 없다. 참조된 후보가 모두 MIPS 바이트였다.
- `FC`(가로 띄우기)가 2,574개 문자열에서 정렬용으로 쓰인다. `F9`(끼워 넣기) 87회, `FA`(숫자) 183회, `F8` 45회.
- 미해결: 이 규칙 밖의 문자열(참조가 없고 참조된 문자열과 사슬로 이어지지도 않은 것)은 모집단에 없다. 런타임에서 화면 문장을 대조해 누락을 확인해야 한다. 압축 파일(`0x74` 머리) 안의 텍스트도 미조사.
- 번역 단위: 원문이 같은 사본은 하나로 묶는다(`tools/units.py`, 키 = 원문 바이트 SHA-1 앞 12자리). 번역 파일 `text/ko/<문맥>.json`(menu 600, stage 702, event 91, climb 61, camp 22, staff 1). 칸 용량은 사본 중 가장 작은 값. 기계 검사는 `tools/kocheck.py`.
- `F8 xx`는 미리 렌더링한 문자열 슬롯 xx를 13px 고정폭으로 최대 8칸 그린다(그리기 단계 0x800177A4). 선택지 앞 커서 자리와 문장 속 주어 자리(플레이어 이름으로 추정, 미확인)에 쓰인다. 이름 뒤 조사는 받침과 무관한 「의」「에게」로 쓴다.
- 원문 추출본: `text/src/<모듈>.json` (`cd tools && python3 textmap.py ../work/files ../tables/charmap.tsv ../text/src`). 일본어 원문이라 저장소에 넣지 않는다.

## 5. 한글 표시 용량

- 한글은 가나가 필요 없으므로 가나·한자 칸(86–251, 252–1261)을 한글로 바꿀 수 있다. 이름 입력에 가나를 남길지에 따라 쓸 수 있는 칸은 약 1,010–1,170자. 1347번 칸은 진행폭 표 밖을 읽어 쓰지 않는다(§3.3).
- 표본 40개 번역(2026-10-21, 크기 측정용 초벌)에서 서로 다른 음절은 319종. 전체 번역에 필요한 음절 수는 번역 후 측정해야 한다.
- 제자리 교체 용량: 자주 쓰는 음절을 1바이트 코드(글리프 ≤ 238)에 배정할 때 표본의 한국어/일본어 바이트 비는 평균 0.88(170음절 배정)–0.93(120음절), 최악 1.22–1.33. 칸을 넘는 문자열은 1–5/40. 1바이트 배정을 표본에 맞췄으므로 낙관적 추정이다.
- 결론: 대부분은 제자리에 들어가지만 일부는 넘친다. 넘치는 문자열은 번역을 줄이거나, 참조가 확인된 문자열(`ref`)에 한해 재배치한다. 빌드는 칸 초과를 오류로 막는다.
- 한글 글꼴 후보: Galmuri11(11px, 12×12 칸에 들어감).
