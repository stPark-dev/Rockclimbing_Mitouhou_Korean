# 초기 조사 — 락클라이밍 미답봉에의 도전 ~알프스 편~ (PS1)

## 1. 지원 원본

| 항목 | 값 |
|---|---|
| 제목 | ロッククライミング 未踏峰への挑戦 アルプス編 (일본판, SLPS-00662, ⓒ 위넷) |
| 구성 | bin/cue 22트랙. 트랙 1 `MODE2/2352` 데이터, 트랙 2–22 CD-DA |
| 트랙 1 크기 | 150,744,384 바이트 (64,092 섹터) |
| 트랙 1 SHA-256 | `86918cf6ae389bd0ef5ab264a0f172d8fcb9d70026a2f25cb7ec3fa9d4b9c6d8` |
| 트랙 1 MD5 | `f4f8bbfd2913d2c92ecc983193aacf29` |
| 부트 | `SYSTEM.CNF` → `SLPS_006.62` |

- ISO 9660. PVD 볼륨 크기는 250,142 섹터로 오디오 트랙까지 덮는다. `CDDA/*.DA` 21개는 오디오 트랙을 가리키는 디렉터리 항목이다.
- 디렉터리 항목 618개 = CD-DA 21 + 영상 STR 58(`MOVIE/`, `MOVIE2/`; 그중 51개가 Form 2 섹터 포함) + 데이터 파일 539. 데이터 파일은 모두 Form 1이고 서브헤더는 본문 `00 00 08 00`, 마지막 섹터 `00 00 89 00`뿐이다.
- 트랙 1의 마지막 파일 `KABE.BIN`은 LBA 63,942에서 끝나고 트랙은 64,092 섹터다. 뒤쪽 여유는 약 150섹터(포스트갭일 수 있음, 미확인)라 **파일을 키워 뒤에 붙이는 방식은 기본으로 쓰지 않는다.** 바꾸는 파일은 원래 섹터 수 안에 들어가야 한다.
- 수정 대상은 트랙 1만이다. 오디오 트랙은 그대로 둔다.

## 3. 글꼴과 인코딩 (확인)

### 3.1 글꼴

- 12×12 픽셀, 4bpp 저장(실제 값 0–3, 2비트 안티에일리어싱), 글자당 72바이트, **1,348자**(97,056바이트).
- 같은 글꼴이 101개 파일에 바이트 단위로 똑같이 들어 있다: `MENU/KWAMENU.BIN` 오프셋 0, `X/X2.BIN`·`SUZU/XI*/SU_IG_*.BIN`·`SUZU/XM_SUZU/SU_MG_*.BIN` 오프셋 0x3E4, `X/X0.BIN` 0x6AC0C, `X_HUMAN/X_STAFF.BIN` 0x1DD90. 각 파일이 실제로 어느 화면의 글꼴 공급원인지는 메뉴 화면(`MENU/KWAMENU.BIN`)만 확인했다.
- `MENU/KWAMENU.BIN` 전체(402,376바이트)가 RAM 0x800E8000에 그대로 올라온다(데이터베이스 화면 RAM 덤프와 전 구간 일치).
- 렌더러는 화면에 나오는 글자만 한 자씩 VRAM에 올린다(3×12 halfword = 12×12 4bpp 업로드, DuckStation VRAM 쓰기 덤프에서 94회 관찰). 업로드된 글리프는 RAM 글꼴 표의 해당 칸과 일치한다.
- 칸 배치: 0–9 숫자, 10–33 기호, 34–59 A–Z, 60–85 a–z, 86–162 히라가나, 163–239 가타카나, 240–251 기타(童 夢 ？ ー ’ ・ ゃゅょャュョ), 252부터 한자. 1262–1265는 △□○×. 0–251은 `tables/charmap_kana.tsv`.
- 252–1347 한자 칸은 아직 문자를 확정하지 않았다. OCR(Noto Sans CJK 템플릿 정합) 1위 정확도는 확인된 32자 기준 약 65%라 육안 판독과 문맥 확인이 필요하다.

### 3.2 문자 코드 (메뉴 모듈 데이터베이스 화면에서 확인)

| 바이트 | 의미 |
|---|---|
| `01`–`EF` | 글리프 `b − 1` (0–238) |
| `F0`–`F4` `xx` | 글리프 `0xEF + ((b − 0xF0) << 8 \| xx)` (239–1518) |
| `FE` | 줄바꿈 |
| `FD` | 문단(쪽) 시작으로 추정 |
| `FF` | 쪽 끝. 뒤에 `00`으로 4바이트 정렬 |

근거: 화면 문장 「△（Ｒ１）ボタン（右手）」이 `KWAMENU.BIN` 0x17928에 `F3 FF 1B 34 02 1C EB B3 D1 1B F2 07 F0 3D 1C`로 있다(△=1262, （=26, Ｒ=51, １=1, ）=27, ボ=234, タ=178, ン=208, 右=758, 手=300). 같은 바이트가 RAM 0x800C7840에 있다.

- `FF`는 2바이트 코드의 둘째 바이트로도 나온다(`F3 FF`=△). 쪽 끝은 토큰 단위로 읽어야만 찾을 수 있다(`tools/textcodec.py` `read_page`). §4의 양 추정은 이 점을 반영하지 않은 바이트 스캔이라 경계가 일부 틀릴 수 있다.
- 렌더러(메인 실행 파일, 0x80017600 부근과 0x80017CC4 부근)는 `F0`–`F4`만 2바이트 선두로 받는다(`slti 0xF5`, `slti 0xF0`). `F5`–`FC`는 2바이트 코드가 아니다.

### 3.3 글자별 진행폭 (확인)

- 1,348바이트 폭 표가 `SLPS_006.62` 오프셋 0x35E80(RAM 0x80045680, t_addr 0x80010000 + 헤더 0x800)에 있다. 숫자 10, 소문자 3–11, 히라가나 9–12, 한자 대부분 13.
- 전역 플래그(gp+0x364)가 켜지면 고정폭 13을 쓴다. 어느 화면에서 켜지는지는 미조사.
- **원작 버그**: 비트맵 경로(0x80017604)는 2바이트 코드를 `((b−0xEF)<<8) − 0x11 + lo` = k로, 진행폭 경로(0x80017CCC)는 `− 0x10` = k+1로 해독한다. 그래서 2바이트 글자 k는 `폭표[k+1]`만큼 진행한다. 1바이트는 `폭표[k]`. 마지막 칸 1347은 표 밖 바이트를 읽으므로 한글 칸으로 쓰지 않는다.
- PoC에서 확인: 이 규칙대로 폭을 넣으면 겹침이 사라지고, 첫 시도처럼 칸 번호대로 넣으면 2바이트 글자 뒤가 겹친다.

## 4. 텍스트 위치와 양

- 루트 `KWAMENU.BIN`(메뉴 모듈)은 헤더 없이 RAM 0x800AFF18에 적재된다. 파일 = 코드 + 데이터, 문자열은 0x10A6C–0x19DD1에 모여 있다.
- 문자열 시작 후보 507개 중 364개는 32비트 직접 포인터, 44개는 `lui/addiu` 쌍으로 참조된다. 나머지 99개는 여러 쪽짜리 문자열의 중간 쪽이거나 오탐일 수 있다(미분류).
- 다른 텍스트 파일: `SUZU_0.BIN`, `SUZU_1.BIN`, `SUZU0`–`SUZU4.BIN`(서로 같은 문자열), `MT0.BIN`·`MT1.BIN`(같음), `KABE.BIN`, `MESI.BIN`, `X_SUZU.BIN`. 이들의 적재 주소와 포인터는 미조사.
- 하위 폴더 파일(`MENU/MENUDB.BIN` 등 `0x74` 머리 파일, `X/*.XX`, `KABEDAT/*`, STR, VB)에서 잡힌 후보는 해독 결과가 무작위라 압축·그래픽 데이터의 우연 일치로 본다. `0x74` 머리 압축 형식에 텍스트가 들어 있을 가능성은 배제하지 못했다.

**초기 양(추정치)**: 루트 파일의 밀집 구간에서 고유 문자열 약 650개, 일본어 약 21,000자, 사용 글리프 882종(그중 한자 약 675종). 문자열 경계를 포인터로 확정하기 전이라 추정치다. 미해결 구간: 압축 파일 내부, 그림 글자, 영상.

## 5. 한글 표시 용량

- 한글은 가나가 필요 없으므로 가나·한자 칸(86–251, 252–1261)을 한글로 바꿀 수 있다. 이름 입력에 가나를 남길지에 따라 쓸 수 있는 칸은 약 1,010–1,170자.
- 번역문 약 2만 자에 필요한 한글 음절은 보통 900–1,100종이라 칸 수가 빠듯하다. 번역에서 쓴 음절만 넣는 방식(빌드가 번역문에서 음절 집합을 뽑아 칸을 배정)이 필요하다.
- 1바이트 코드(글리프 0–238)에 자주 쓰는 음절을 배정하면 문자열 바이트 수가 일본어와 비슷하게 유지된다.
- 글꼴 칸을 1,348개보다 늘리려면 101개 사본이 있는 파일들이 커지고, 글꼴 뒤에 다른 데이터가 있어 제자리 확장이 안 된다. 기본안에서는 늘리지 않는다.
- 한글 글꼴 후보: Galmuri11(11px, 12×12 칸에 들어감).

## 8. 대표 PoC 기록 (2026-10-21)

- 목적: 글꼴 칸 교체 → 화면 표시 경로, 1바이트·2바이트 코드 양쪽, 진행폭 처리를 한 화면에서 확인.
- 빌드: `tools/poc_db.py` (원본 트랙 1 SHA-256 `86918cf6…`에서 시작). 바꾼 파일 3개, 모두 제자리:
  - `KWAMENU.BIN` 0x1790D–0x17926(26바이트): 「まず、移動しようと思う手や足を選びます。」 → 「먼저 손발을 고릅니다。」 + 2바이트 공백으로 길이 맞춤.
  - `MENU/KWAMENU.BIN` 글꼴 칸 60–65(1바이트 코드), 1250–1254(2바이트 코드)를 Galmuri11 한글·공백으로.
  - `SLPS_006.62` 폭 표: 1바이트 칸은 k, 2바이트 칸은 k+1 위치에 한글 12, 공백 6.
- 결과 이미지 SHA-256 `f4bdbab24c652b87d14b2d27ec3b58e023a1de0efada034ffe4efb128eb8f21a`. 화면(데이터베이스 → クライマーの操作法 → フリークライミング → 基本的な移動)에서 한국어 줄이 겹침 없이 표시. 나머지 일본어 줄은 그대로.
- 판정: 통과. 확립된 것 — 메뉴 화면 글꼴 공급원 = `MENU/KWAMENU.BIN`, 문자 코드 공식(양쪽 폭), 진행폭 표 위치와 k+1 규칙. 이 판정은 메뉴 모듈에만 해당한다.
- 첫 시도(폭 표 미수정)에서는 소문자 칸 글자가 원래 폭(7–9)으로 겹쳤고, 두 번째 시도(폭을 칸 번호 k에 넣음)에서는 2바이트 마지막 글자 뒤가 겹쳤다. 렌더러 역어셈블로 k+1 규칙을 확인한 뒤 세 번째 시도에서 통과.
